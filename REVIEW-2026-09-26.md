## Feasibility: auto-sourcing missing capabilities from the internet (2026-09-26)

Ask: when routing finds no skill/tool/MCP for a request, search the internet (free only),
install into the agent-fleet store, wire all harnesses, and use it.

**Verdict: yes — ~80% of the machinery exists; the missing 20% is one sourcing stage in the
router plus a safety fence. Buildable in ~250-300 lines, no new services or dependencies.**

Already in place (verified live):
| Piece | Status |
|---|---|
| Gap detection | pipeline card already emits "No capability scored above threshold" + coverage line when zero picks (pipeline.py:902, :98) — the trigger hook exists |
| Registry search | `hermes skills search <topic> --json` aggregates 15 free sources (skills-sh, official, anthropic, openai, github, clawhub, lobehub, huggingface, nvidia…) |
| MCP discovery | official MCP registry (registry.modelcontextprotocol.io, free, API-first) + PulseMCP/Glama/mcp.so directories via web_search; all free |
| Install | `hermes skills install <id> -y`; fallback `git clone --depth 1` + `cp` (dodges GitHub API rate limits); prereq probing pattern documented in agent-skill-sourcing |
| Fleet store | ~/Work/infra/agent-fleet: skills/ superset, mcp/ per-harness defs, sync-from-desktop.sh (6h timer), harness/*.sh legs for claude/opencode/gemini/hermes/antigravity |
| All-harness wiring | established ordering: Hermes config first, then ~/.claude.json, opencode, agy, fleet store in the same pass |
| Pick-up-and-use | `~/.tool-router/index --cwd .` rebuilds; dense lane embeds incrementally; next route surfaces the new skill — works today |

Proposed design (stage 5 — "source", proposal-gated, never auto):
1. **Gap signal**: when pipeline returns zero picks AND laya low-conf, card gains one line:
   `no local capability matched — run ~/.tool-router/source "<query>" to search registries`.
   Never triggers an install by itself.
2. **Search** (`route.py --source "<query>"`): hermes skills search across sources (JSON) +
   web_search for MCP registries; dedupe against index + installed inventory.
3. **Score candidates**: install counts (1K+ floor), recency (~3mo commits), license
   (open-source), **free = no paid API key required** — scan README/description for
   paid-tier/API-key signals; laya screen_content on every untrusted description (injection
   fence) before anything reaches the table.
4. **Present table → user approves each install** (the HITL gate; non-negotiable for MCPs).
5. **Install + wire**: skills → Hermes → fleet skills/ → commit+push (skip the 6h wait) →
   mirror to claude/opencode/gemini legs. MCPs → local config blocks in fleet order, machine
   secrets to ~/.hermes/.env, never in the repo.
6. **Verify + use**: index rebuild (dense auto-embeds), reroute the original query, confirm
   the new capability appears on the card and gets used.

Why not fully automatic (recorded deliberately):
- **One routing miss ≠ missing capability.** Hybrid routing still misses on phrasing; auto-install
  on every miss would bloat 5 harnesses with junk. Guard: only propose when a *similar gap*
  repeats N times (track gaps in a state file, like learned.json) or on explicit ask.
- **Registries are untrusted text.** A skill description is attacker-controllable input;
  screen_content screening + human approval on the shortlist is the fence.
- **"Free to install" ≠ "free to run".** An open-source MCP can demand a paid API key;
  prereq probing before recommending is mandatory (agent-skill-sourcing pitfalls).

Tier 2 (later, opt-in): auto-install skills-only for repeat gaps, capped N/month, full audit
log; MCPs and plugins always gated.

## Round 2: why Laya declined 4/10, and the real fix (2026-09-26, commit 2cab6cf)

Patience to 10s alone did NOT move the number — instrumentation of the 4 declined probes
(laya raw answers, 10s window) showed all answered in ~1s with *correct* picks:

| probe | laya pick | p1 | margin | verdict under old gate |
|---|---|---|---|---|
| review elixir phoenix auth bugs | review-elixir ✓ | 0.246 | 0.022 | vetoed |
| our REST endpoints take 4s | rest-api-design ✓ | 0.304 | 0.077 | vetoed |
| nightly backups postgres | prisma-postgres | 0.318 | 0.029 | vetoed |
| top 20 tools competitor research | tool-router-engineering (baited by literal phrase) | 0.290 | 0.065 | vetoed (decline was right, pick wrong) |

Diagnosis: over 5 similar candidates the classifier's mass flattens toward uniform (1/N=0.20);
correct picks score p1 0.25–0.32, margins 0.02–0.08. The fixed margin≥0.10 gate vetoes almost
everything — it was mis-calibrated, not slow.

Fixes (all committed 2cab6cf, selftest 18/18):
1. `gate_accept(p1, margin, n_opts)` in laya_rerank.py — accepts when p1 ≥ 1.2×uniform AND
   margin ≥ 0.02, or legacy p1 ≥ 0.75. t_laya_gate covers the 4 real cases + negative space.
2. config timeout_s 0.6→2.0 (round 1) → 10.0 (this round, per instruction).
3. airtable description (3 identical copies patched) no longer leads with "REST API".

Bench after fixes: laya fires **10/10** probes (was 6/10), rewriter 10/10 (confound removed by
running ablation variants rewrite-free), nodense ablation clean (0 semantic tags). REST misroute
gone from top-3 in ALL variants — cured at the source, not downstream. Reorders vs BM25 order
are quality-positive: review-elixir promoted to #1 for the phoenix probe; plugin-settings to #1
for the settings probe. Cost: median 4.0s for a full-pipeline explicit card (fast-path hook
routes stay sub-second; rerank adds ~1s when enabled there).

Open observation (not fixed, deliberate): the competitor probe — Laya's pick was baited by the
literal phrase "tool router" in the request; the gate now accepts its decline-correctness in
general but this probe's top-1 remains tool-router-engineering (defensible: user explicitly
asked to "use the tool router"). instruction-following vs intent — recorded, no change.
